# Правила командной разработки «Тыкуэн»

Документ фиксирует внутренние стандарты команды: работу с Git, оформление коммитов, стиль кода, комментарии и процедуру code review. Правила обязательны для всех участников.

## 1. Ветки

| Ветка                      | Назначение                                                                 |
| -------------------------- | -------------------------------------------------------------------------- |
| `main`                     | Стабильная версия, которую показываем на защите. Прямые коммиты запрещены. |
| `develop`                  | Интеграционная ветка. Сюда вливаются все задачи после ревью.               |
| `feature/<номер>-<кратко>` | Новая функциональность: `feature/12-login-form`                            |
| `bugfix/<номер>-<кратко>`  | Исправление ошибки: `bugfix/31-chat-scroll`                                |
| `docs/<номер>-<кратко>`    | Документация и отчёты: `docs/5-lab3-report`                                |
| `chore/<номер>-<кратко>`   | Настройка, зависимости, CI: `chore/40-github-actions`                      |

- `<номер>` — номер задачи (issue) в GitHub.
- Имя ветки — латиницей, в нижнем регистре, слова через дефис.
- Ветка создаётся от актуального `develop` и удаляется после слияния.
- `develop` вливается в `main` по завершении этапа (лабораторной) через PR.

```bash
git switch develop
git pull
git switch -c feature/12-login-form
```

## 2. Коммиты

Используем [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```
<тип>(<область>): <что сделано> #<номер задачи>
```

Типы: `feat` — функциональность, `fix` — исправление, `docs` — документация, `style` — форматирование, `refactor` — рефакторинг без изменения поведения, `test` — тесты, `chore` — настройка и зависимости.

Примеры:

```
feat(auth): форма входа по email и паролю #12
fix(chat): прокрутка к последнему сообщению #31
docs: отчёт по лабораторной работе 3 #5
```

- Описание — на русском, в повелительном или прошедшем времени, без точки в конце, до 72 символов.
- Один коммит — одно логическое изменение.
- Номер задачи обязателен: так коммит автоматически связывается с issue.

## 3. Стиль кода

- Язык — **TypeScript** в строгом режиме (`strict`). Тип `any` запрещён, кроме обоснованных случаев с комментарием.
- Форматирование — **Prettier** (`.prettierrc.json`): одинарные кавычки, точка с запятой, ширина строки 100.
- Статический анализ — **ESLint** (`eslint.config.js`). Код с ошибками линтера не принимается.
- Отступы, кодировка и переводы строк — `.editorconfig` (2 пробела, UTF-8, LF).
- Перед отправкой PR каждый запускает:

```bash
npm run lint && npm run typecheck && npm test
```

### Именование

| Что                         | Стиль            | Пример                         |
| --------------------------- | ---------------- | ------------------------------ |
| Компоненты React и их файлы | PascalCase       | `ListingCard.tsx`              |
| Функции, переменные, хуки   | camelCase        | `formatPrice`, `useFavorites`  |
| Константы                   | UPPER_SNAKE_CASE | `MAX_PHOTOS`                   |
| Типы и интерфейсы           | PascalCase       | `Listing`, `DealType`          |
| Таблицы и колонки БД        | snake_case       | `listing_images`, `created_at` |

### Структура `src/`

```
src/
  app/         — корневой компонент приложения
  pages/       — страницы (собирают фичи в экран)
  features/    — функциональные модули: auth, listings, chat, favorites…
  components/  — переиспользуемые UI-компоненты
  hooks/       — общие React-хуки
  lib/         — клиенты внешних сервисов (Supabase)
  services/    — работа с данными: запросы к БД и Storage
  types/       — общие типы TypeScript
  styles/      — глобальные стили
  test/        — настройка тестового окружения
```

- Один компонент — один файл. Компонент длиннее ~200 строк делится на части.
- Тесты лежат рядом с тестируемым модулем: `App.tsx` → `App.test.tsx`.

## 4. Комментарии

- Комментарий объясняет **почему**, а не **что** делает код. Очевидный код не комментируется.
- Публичные функции и компоненты из `shared/` описываются JSDoc-комментарием (`/** … */`).
- Комментарии пишутся на русском.
- Временные места помечаются `// TODO(#номер): описание` — только со ссылкой на задачу.
- Закомментированный код не коммитится.

```ts
/** Форматирует цену в рублях: 25000 → «25 000 ₽». */
export function formatPrice(value: number): string { … }

// Лимит проверяется ещё и триггером в БД: фронтенду доверять нельзя.
if (todayCount >= 1) { … }
```

## 5. Pull Request и code review

1. Задача готова → `git push` ветки → открыть PR в `develop`.
2. Заполнить шаблон PR: что сделано, ссылка на задачу (`Closes #12`), как проверить, скриншоты для UI.
3. Назначить ревьюера — **любого другого участника команды**. Автор не может одобрить свой PR.
4. Ревьюер в течение 24 часов проверяет:
   - соответствие задаче и требованиям `PROJECT_CONTEXT.md`;
   - читаемость, именование, отсутствие дублирования;
   - обработку ошибок и состояний загрузки;
   - безопасность (RLS, валидация, отсутствие секретов в коде);
   - наличие тестов для логики.
5. Замечания оставляются комментариями к строкам. Автор исправляет и отвечает на каждое.
6. Слияние — после **1 одобрения (Approve)** и прохождения проверок, способом **Squash and merge**. Ветка удаляется.

Тон ревью — уважительный и конкретный: «предлагаю вынести в `formatPrice`, так как дублируется в двух местах» вместо «плохо».
