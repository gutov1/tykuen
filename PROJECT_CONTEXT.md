# ТЫКУЭН — PROJECT CONTEXT

## 1. О ПРОЕКТЕ

Название продукта: Тыкуэн

Язык интерфейса: русский.

Регион запуска: Кабардино-Балкарская Республика (КБР).

Тыкуэн — локальное молодежное веб-приложение/PWA для людей из КБР.

Основная идея:

Тыкуэн не является классическим маркетплейсом и не должен превращаться в копию Avito.

Это локальная площадка, где обычные люди могут:

- продать ненужные вещи;
- отдать вещи бесплатно;
- обменяться вещами;
- предложить услуги;
- найти нужные вещи;
- договориться друг с другом напрямую.

Сама сделка происходит полностью офлайн между пользователями.

Тыкуэн НЕ участвует в передаче денег, доставке или физической передаче товара.

Никаких комиссий.

Никакой встроенной оплаты.

Никакой доставки.

Никаких платных поднятий объявлений.

Никакой внутренней рекламы.

---

# 2. ЦЕЛЕВАЯ АУДИТОРИЯ

Основная аудитория — молодежь и обычные жители КБР.

Продукт должен ощущаться:

- современным;
- легким;
- локальным;
- дружелюбным;
- молодежным;
- визуально ярким;
- простым.

Не нужно делать интерфейс похожим на корпоративный интернет-магазин.

Не нужно копировать визуальный стиль Avito.

---

# 3. ОСНОВНОЙ USER FLOW

Пользователь:

1. Регистрируется через email + пароль.
2. Указывает имя.
3. Выбирает свой населенный пункт КБР.
4. Попадает на главную.
5. Видит категории.
6. Может искать товары или услуги.
7. Открывает объявление.
8. Может добавить его в избранное.
9. Может написать владельцу.
10. Пользователи договариваются в обычном текстовом чате.
11. Встречаются офлайн.
12. После сделки продавец самостоятельно нажимает "Продано".
13. Объявление исчезает из активной ленты и переходит в "Проданные" профиля.
14. Чаты при этом сохраняются.

---

# 4. АВТОРИЗАЦИЯ

Регистрация:

- имя;
- email;
- пароль;
- повтор пароля;
- населенный пункт.

Email подтверждать НЕ нужно.

Телефон НЕ нужен.

SMS НЕ нужен.

Google/Apple/VK/Telegram авторизация НЕ нужна.

После регистрации пользователь сразу может пользоваться приложением.

Один email = один аккаунт.

Должна быть функция:

"Забыли пароль?"

Через стандартный механизм восстановления пароля по email.

---

# 5. НАСЕЛЕННЫЕ ПУНКТЫ

При регистрации пользователь выбирает населенный пункт из заранее подготовленного списка населенных пунктов КБР.

Не использовать свободный ввод в качестве основного способа выбора.

В профиле можно изменить населенный пункт.

При создании объявления пользователь может выбрать местоположение товара отдельно от своего места проживания.

Например:

Профиль:
Нальчик

Объявление:
Баксан

Это разрешено.

В объявлении отображается:

📍 Нальчик

или:

📍 Нальчик, Центр

Точный адрес не требуется и не должен публиковаться.

---

# 6. ГЕОГРАФИЯ ЛЕНТЫ

Пользователь видит объявления всей КБР.

По умолчанию объявления его населенного пункта могут быть показаны первыми, но приложение не должно ограничивать пользователя только его городом.

Пользователь должен иметь возможность переключиться на другой населенный пункт/всю КБР.

# 8. ТОВАРЫ

Поля объявления товара:

- название;
- категория;
- максимум 5 фотографий;
- способ сделки;
- цена;
- состояние;
- описание;
- населенный пункт/местоположение.

Однако поле "состояние" НЕ использовать.

Для товара достаточно:

- название;
- категория;
- до 5 фотографий;
- способ сделки;
- цена;
- описание;
- местоположение.

# 9. УСЛУГИ

- цена;

- местоположение.

# 10. СПОСОБ СДЕЛКИ

Для товара пользователь может выбрать максимум два варианта:

1. Продам
2. Обменяю

ИЛИ:

3. Отдам бесплатно

Если выбран "Отдам бесплатно", другие варианты выбрать нельзя.

Если выбраны "Продам" и "Обменяю", доступны оба варианта.

Например:

💰 Продам
🔄 Обменяю

При продаже пользователь указывает:

- точную цену;
- либо "Цена договорная";
- либо "Предлагайте цену".

При бартере пользователь ОБЯЗАТЕЛЬНО пишет, на что готов обменять.

Например:

"Обменяю на велосипед или игровую приставку."

Для бесплатной передачи:

🎁 Бесплатно

Цена не требуется.

Все суммы указываются в рублях ₽.

# 11. ОГРАНИЧЕНИЯ НА ОБЪЯВЛЕНИЯ

Один пользователь может создать максимум:

1 новое объявление за 24 часа.

Удаление объявления НЕ сбрасывает это ограничение.

То есть после создания объявления пользователь не может удалить его и сразу создать новое.

Максимум активных объявлений пользователя:

50.

Редактирование существующего объявления НЕ считается новым объявлением.

Редактирование НЕ поднимает объявление вверх ленты.

# 20. СООБЩЕНИЯ

В приложении есть личные текстовые чаты.

Начать чат можно:

1. из объявления;
2. из профиля пользователя.

Сообщения:

- только текст;
- поддержка emoji;
- дата/время;
- статус прочтения.

Без:

- голосовых;
- файлов;
- фотографий;
- видео.

При переходе из объявления в чат желательно показывать компактную карточку объявления в верхней части чата.

Несколько пользователей могут одновременно писать владельцу одного объявления.

После нажатия "Продано" чаты НЕ удаляются.

# 21. СТАТУС ОБЪЯВЛЕНИЯ

- переходит в "Проданные" профиля;

# 22. ЖАЛОБЫ

- другое.

На первом этапе админ-панель НЕ создавать.

# 24. PWA

Приложение должно быть полноценной PWA.

Оно должно:

- устанавливаться на телефон;
- устанавливаться на desktop;
- иметь manifest;
- иметь иконку;
- иметь название "Тыкуэн";
- работать как установленное приложение;
- иметь responsive layout.

При этом Тыкуэн должен оставаться обычным веб-сайтом, который открывается в браузере.

Offline-first функциональность не является обязательной.

Критически важные данные требуют подключения к интернету.

---

# 25. DESIGN

Стиль:

Современный молодежный минимализм + playful элементы.

Не копировать Avito.

Основные характеристики:

- светлый интерфейс;
- яркий фирменный акцент;
- много воздуха;
- красивые округлые карточки;
- современная типографика;
- мягкие тени;
- аккуратные границы;
- выразительные кнопки;
- понятная иерархия;
- mobile-first;
- при этом полноценный desktop.

Цветовую палитру Claude должен подобрать самостоятельно.

Не использовать темную тему.

Не перегружать интерфейс анимациями.

На первом этапе использовать только минимальные transition/micro-interactions там, где они улучшают UX.

Не делать тяжелые декоративные анимации.

- TypeScript;

- переиспользуемые компоненты;
- отсутствие очевидного дублирования;
- обработка ошибок;
- loading states;

---

# 31. CLAUDE AUTONOMY

Claude Code должен работать максимально автономно.

Если техническое решение не меняет пользовательские требования, Claude принимает решение самостоятельно.

Claude должен спрашивать пользователя только тогда, когда:

- требование неоднозначно;
- решение существенно меняет UX;
- решение противоречит этому документу;
- невозможно продолжить без пользовательского решения.

В остальных случаях:

решение → реализация → проверка → продолжение.

Не спрашивать "Продолжить?" после каждого шага.
